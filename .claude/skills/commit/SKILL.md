# commit

변경사항을 읽기 좋은 커밋 이력으로 남기는 스킬. 이력은 팀이 함께 읽으므로 한 커밋에는 한 가지 이유만 담는다. 커밋 요청 자체가 실행 승인이므로 별도 확인 없이 진행하고, 결과를 보고한다.

## 절차

### 1. 변경사항 분석
- `git status`로 변경·추가·삭제 파일을 확인한다.
- `git diff`(unstaged)와 `git diff --staged`(staged)를 읽는다. 새 파일(untracked)은 내용을 직접 읽는다.
- git 저장소가 아니면(`git rev-parse` 실패) 그 사실을 알리고 중단한다. `git init`은 요청이 있을 때만 한다.
- 변경이 없으면 "커밋할 변경사항이 없다"고 알리고 끝낸다.
- `.env`, 키·토큰 등 비밀 값이 들어간 파일은 커밋 대상에서 빼고 사용자에게 알린다. 값은 출력하지 않는다.

### 2. 논리적 단위로 분류
- 목적이 같은 변경끼리 묶는다. 예: 버그 수정과 무관한 리팩토링은 분리, 기능과 그 테스트는 함께.
- 분류마다 포함할 파일 목록(필요하면 hunk 단위)을 정한다. 한 파일에 서로 다른 목적의 변경이 섞였으면 그 사실을 계획에 적는다.
- 변경이 작고 목적이 하나면 커밋 1개로 충분하다. 억지로 쪼개지 않는다.

### 3. 한국어 커밋 메시지 작성
형식: `type: 요약` (범위가 분명하면 `type(scope): 요약`)

| type | 용도 |
|---|---|
| feat | 사용자에게 보이는 새 기능 |
| fix | 버그 수정 |
| refactor | 동작 변경 없는 구조 개선 |
| chore | 빌드·설정·의존성·문서 등 그 외 |

- 요약은 한 줄, 50자 안팎, 마침표 없이 "~추가", "~수정", "~분리"처럼 끝맺는다.
- 무엇을 했는지보다 왜 필요한지가 diff만으로 안 드러날 때만 빈 줄 뒤에 본문을 덧붙인다.
- 프로젝트에 기존 커밋 규칙이 있으면(`git log`에서 확인) 그쪽을 우선한다.
- 시스템·사용자 지침에 커밋 트레일러(예: Co-Authored-By)가 지정되어 있으면 메시지 끝에 붙인다.

### 4. 바로 커밋
승인을 기다리지 않고 분류한 순서대로 커밋한다.

- 커밋 단위마다 해당 파일만 `git add <파일>`로 스테이징하고 커밋한다. `git add -A`/`.`는 쓰지 않는다. 분류에 없는 파일이 딸려 들어가기 때문이다.
- 끝나면 아래 형식으로 결과를 보고한다. 잘못 나뉘었다면 사용자가 알려 줄 수 있도록 파일 목록까지 보여준다.

```
커밋 완료 (총 N개)
1. feat: 프롬프트 입력창에 예시 버튼 추가
   - src/components/PromptInput.tsx
   - src/components/PromptInput.test.tsx
2. chore: eslint 규칙 갱신
   - eslint.config.js
```

- 사용자가 나중에 메시지나 분류를 고치라고 하면 `git reset --soft`로 되돌려 다시 커밋한다. 이는 방금 만든 로컬 커밋에만 쓴다.
- `push`는 하지 않는다. 사용자가 따로 요청할 때만 한다.
- pre-commit 훅이 실패하면 원인을 알리고 고친 뒤 새 커밋으로 만든다. `--no-verify`나 `--amend`로 우회하지 않는다.
