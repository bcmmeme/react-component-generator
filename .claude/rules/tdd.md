# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.**
> 단계를 건너뛰거나 순서를 바꾸거나 "이번만 예외"를 만들지 않는다. 예외는 아래 "적용 기준"에 적힌 것뿐이다.

## 우선순위

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선**한다.
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙이 다루지 않는 부분에만 적용한다.

## 적용 기준

### TDD 필수

- 비즈니스 로직
- API (엔드포인트, 요청/응답 처리, 에러 매핑)
- 유틸리티·순수 함수
- 버그 수정 (**버그를 재현하는 실패 테스트를 먼저 작성**)
- 기존 동작을 바꾸는 리팩토링 (테스트가 없으면 먼저 현재 동작을 고정하는 테스트를 추가)

### TDD 불필요

- 타입 정의 (`type`, `interface`)
- 설정 파일 (tsconfig, eslint, vite 설정 등)
- 순수 UI (로직 없는 마크업·스타일)
- SQL (스키마, 마이그레이션, 단순 쿼리)

판단이 애매하면 **필수로 간주한다.** 로직(분기, 계산, 상태 전이)이 하나라도 있으면 순수 UI가 아니다.

## RED-GREEN-REFACTOR

### 1. RED — 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 않는다.
- 테스트 이름은 동작을 서술한다.
- **반드시 실행해서 실패를 확인한다.** 실행하지 않은 테스트는 RED가 아니다.
- **실패 이유가 "기능 미구현"이어야 한다.** 문법 오류, import 실패, 오타, 잘못된 셋업으로 인한 실패는 RED가 아니다. 테스트를 고쳐서 올바른 이유로 실패하게 만든다.
- 처음부터 통과하는 테스트는 아무것도 증명하지 못한다. 동작이 이미 있는지, 테스트가 잘못됐는지 확인한다.

### 2. GREEN — 테스트를 통과시키는 최소 코드

- **테스트를 통과시키는 최소한의 코드만 작성한다.** 하드코딩이어도 괜찮다. 다음 RED가 일반화를 강제한다.
- **YAGNI.** 지금 테스트가 요구하지 않는 분기, 옵션, 추상화를 넣지 않는다.
- **신규 테스트와 기존 테스트가 모두 통과하는지 실행해서 확인한다.** 새 테스트만 돌리고 끝내지 않는다.
- 통과시키려고 테스트를 약하게 고치지 않는다. 테스트가 틀렸다면 RED로 돌아가 고친다.

### 3. REFACTOR — 정리

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **모든 테스트가 green인 상태를 유지한다.** 작은 단위로 바꾸고 매번 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작이 필요하면 RED로 돌아간다.
- 리팩토링 중 테스트가 깨지면 직전 변경을 되돌린다.

### 4. 반복

- 다음 동작이 남았으면 **새 RED로 돌아간다.** 한 번에 여러 동작을 구현하지 않는다.
- 더 이상 필요한 동작이 없을 때 종료한다.

## 삭제 강제 규칙

- **테스트 전에 프로덕션 코드를 먼저 작성했다면, 그 코드를 삭제하고 RED부터 다시 시작한다.**
- **"참고용"으로 남기는 것도 금지한다.** 주석 처리, 임시 파일, 다른 브랜치 보관, 복사해 두고 보면서 다시 쓰기 모두 포함한다.
- 삭제 후 테스트부터 작성하고, 코드는 GREEN 단계에서 새로 쓴다.
- 이 규칙을 어긴 사실을 발견하면 **즉시 멈추고 삭제한 뒤 사용자에게 알린다.**

## 변명 차단표

| 변명 | 반론 |
|---|---|
| "너무 단순해서 테스트가 불필요하다" | 단순한 코드는 테스트도 단순하다. 몇 줄이면 끝나는 비용이고, 단순한 코드가 나중에 복잡해질 때 회귀를 막는 안전망이 된다. |
| "나중에 테스트를 추가하겠다" | 나중에 쓴 테스트는 구현을 따라 쓰게 되어 버그까지 정답으로 고정한다. 그리고 그 "나중"은 오지 않는다. |
| "시간이 없다" | 테스트 없는 코드는 디버깅과 수정에 더 많은 시간을 쓰게 한다. 급할수록 실패를 빨리 잡아주는 사이클이 필요하다. |
| "삭제하면 낭비다" | 매몰비용이다. 테스트 없이 쓴 코드는 검증되지 않은 부채이고, 이미 아는 내용을 다시 쓰는 것은 빠르다. 남겨두면 테스트가 코드에 맞춰진다. |
| "프로토타입이다" | 프로토타입은 검증 후 버려야 할 때만 성립한다. 그대로 제품 코드가 되는 경우가 대부분이다. 버릴 코드라면 아예 이 규칙의 대상이 아니므로 먼저 사용자와 합의한다. |
